For the first version, I would make the flow:

1. Resolve the job URL and identify its backend, employer, and job ID.
2. Read the posting and discover the actual application fields, including conditional questions.
3. Select or generate the appropriate résumé using the existing company/job context.
4. Populate factual fields, reuse suitable answers, and generate drafts for unanswered narrative questions.
5. Show the completed application for review, then submit when authorized.
6. Record the submitted answers, exact PDF hash, and confirmation.

Each integration should translate its form into one shared representation: question, field type, required status, choices, length limits, and dependencies. Selenium can own browser interaction; the Codex integration can supply structured answer drafts. That separation makes failures easier to diagnose and keeps routine form filling from consuming tokens.

Your **SQLite answer library is a useful part of this design**, but I would distinguish three kinds of information:

- **User-confirmed facts:** contact details, qualifications, preferences, and eligibility answers. Populate these directly; missing facts should prompt the user rather than be invented.
- **Reusable narratives:** examples of leadership, difficult migrations, incident response, or collaboration. Save approved answers and the experience supporting them.
- **Company/job-specific answers:** "Why this company?" or "How does your experience fit this role?" Keep these scoped to the employer and posting.

The important cache rule is that **question text alone is not a sufficient key**. Reuse should account for the applicant, question meaning, available choices, length limit, relevant profile facts, and company/job context. Two forms asking about sponsorship in different countries must not accidentally share an answer.

TTL makes sense for generated drafts. I would expose a default expiration interval, overrides by answer category, and an explicit refresh option. Expiration should trigger regeneration **when the answer is next needed**, avoiding background token usage. Changes to supporting facts or job requirements should invalidate an answer immediately, even before its TTL expires. User-edited answers should remain preserved as versions; regeneration should not silently overwrite them.

I would also store application history separately from the answer cache. If submission times out, the application should become "confirmation unknown," not automatically retry the final submission and risk a duplicate. Retrying reads and draft generation with exponential backoff is straightforward; submission needs reconciliation.

For browser login, MFA, or CAPTCHA, keep the session open and let the user finish, then resume from the saved step. I would initially run applications locally, keeping the answer database and browser sessions outside Git.

My suggested first milestone is **Greenhouse applications completed through the review step, with reusable answers and resumable sessions**.
